------------------------------------------------------------
PRODUCT SUMMARY
------------------------------------------------------------

Partner AI Launchpad is a reusable OpenShift-based lab platform for Red Hat/Intel partner and client demos.

It provides three experiences:

1. Quick Start Labs
Prebuilt, guided, fast-start demos.

2. Guided Build Areas
Semi-open, template-driven build spaces for AI ideas.

3. Open Sandboxes
Flexible partner/client namespaces with quotas, tools, observability, and optional model/hardware access.

The platform should support:
- Red Hat internal teams
- Intel teams
- OEM/partner teams
- customers/clients
- reusable labs after Summit
- ephemeral and persistent sessions
- namespace-based tenancy to start
- sandbox security boundaries
- URL-based handoff
- branding separation
- observability by default
- chargeback/showback reporting
- integration points for Babylon, Pool Boy, and Anarchy Gov
- AI-assisted generation of AAP/OpenShift lab assets, later

------------------------------------------------------------
CORE DESIGN RULES
------------------------------------------------------------

1. Repeatability over cleverness.

Every catalog item must be provisioned the same way every time.

2. Catalog-first.

Users request catalog items, not random hand-built environments.

3. Adapter-based.

The app must not hardcode Babylon, Pool Boy, Anarchy Gov, OpenShift, AAP, GitOps, or Tekton into the core domain model.

Those systems are adapters.

4. Namespace tenancy first.

Use namespace-per-lab or namespace-per-session as the initial isolation model.

5. Observable by default.

Every lab gets a dashboard/reporting view.

6. URL handoff.

Every successful lab produces a URL and handoff package.

7. Validation before ready.

A lab is not ready just because provisioning completed. It is ready only when validation passes.

8. Showback from day one.

Track tenant, lab, resources, duration, and usage metadata even if actual cost calculation is mocked.

9. Branding by config.

Do not fork the app per partner/client. Use branding profiles.

10. AI-assisted generation is proposal-first.

AI may later generate AAP/OpenShift/GitOps/lab guide artifacts, but those must be validated before use.

------------------------------------------------------------
PROVISIONING LIFECYCLE
------------------------------------------------------------

Every lab session must follow this lifecycle:

1. submitted
2. accepted
3. planning
4. provisioning
5. validating
6. ready
7. active
8. expired
9. resetting
10. reclaimed

Failure states:
- rejected
- failed
- validation_failed
- cleanup_failed

Implement lifecycle transitions as deterministic functions.

A transition should:
- validate current state
- validate target state
- record timestamp
- record reason/evidence
- persist event

Do not allow impossible transitions.

Example:
ready → provisioning is invalid.
failed → reclaimed may be valid after cleanup.
active → resetting is valid.
expired → reclaimed is valid.

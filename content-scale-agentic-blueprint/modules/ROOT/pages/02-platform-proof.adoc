= Prove the Governed Agent Runtime

== One Journey, Three Proof Views

Use the three learner views together. They are different views of the same
workload and the same journey ID—not separate product exercises.

[cols="1,2,2",options="header"]
|===
| View | Use it to answer | Do not use it for
| OpenShift terminal | Which namespace, pods, replicas, revisions, and bounded
  workload controls are active? | Editing cluster-wide resources or bypassing
  the lab controls
| OpenShift Console | Is the workload healthy, scheduled, scaling, or recovering?
  Which deployment and pod changed? | Replacing correlated journey evidence
  with a visual assumption
| OpenTelemetry trace | Where did time and failure occur from intake through
  agents, MCP, policy, Intel Xeon inference, and human review? | Exposing
  credentials, hidden reasoning, or unredacted sensitive prompts
|===

== Agent Sandbox: Govern Every Execution

The agent sandbox is a governance layer around each specialized agent. It sits
between orchestration and external access so an agent cannot reach tools,
networks, files, credentials, or compute merely because a model requested it.

For one running agent, verify the sandbox contract:

* a dedicated workload identity and least-privilege service account;
* allowlisted MCP tools and read-only access by default;
* namespace and network boundaries around reachable services;
* read-only root filesystem, dropped Linux capabilities, seccomp, and bounded
  CPU and memory where the workload supports them;
* no direct production action path from model output; and
* an audit event for every allowed or denied external request.

Where the cluster provides OpenShift Sandboxed Containers, the lab may add the
`kata` runtime class as a stronger workload-isolation boundary. This runs the
agent workload in a lightweight virtual machine. It complements the logical
agent policy; it does not replace tool authorization, deterministic policy, or
human authority. If Kata is not installed and certified for this environment,
label that control `UNAVAILABLE` and evaluate the standard OpenShift isolation
controls without claiming VM-backed isolation.

== Terminal Session: Inspect the Sandbox Contract

Open the supplied terminal and confirm the assigned namespace. Inspect the
agent workload identity, security context, network policy, resource limits,
runtime class, and approved tool configuration. Record the observed values and
their source state. Do not mutate cluster-wide policy from the learner session.

== OpenShift Console Session: See Platform State

Open the OpenShift Console in the supplied namespace. Locate the orchestrator,
specialized agents, MCP service, and presentation/workspace routes. Relate each
deployed resource to the agentic blueprint before changing load.

Keep this view open during the baseline and pressure runs. Pod readiness,
restart count, placement, and replica transitions explain platform behavior;
they do not prove the quality of an agent decision.

== OpenTelemetry Session: Follow the Journey

Open the lab-provided trace view and search by the journey ID created in the
next step. A complete trace must correlate intake, orchestration, every agent,
MCP evidence collection, deterministic policy, Intel Xeon inference, and the
review-required boundary.

The trace should expose component identity, timestamps, status, and approved
latency attributes. Model prompt and response fields must follow the lab's
redaction policy. If the collector, trace backend, or correlation fields are
unavailable, label the trace `UNAVAILABLE` and stop the certification path; do
not substitute screenshots or generated examples.

== Platform Proof Checkpoint

You can trace one agent request across its governed sandbox, OpenShift runtime,
MCP boundary, Intel Xeon inference request, and human-review boundary using one
correlation identity.

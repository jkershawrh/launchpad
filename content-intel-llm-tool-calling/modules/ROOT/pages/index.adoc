= Build an AI Tool Calling System from Scratch

Welcome to the *vLLM Tool Calling on OpenShift AI* lab. In this hands-on workshop you will build a complete tool calling system -- from understanding the protocol, to verifying a platform-managed model endpoint, to writing an automated multi-tool application. Inference is supplied by the Launchpad MaaS service on {intel_platform} processors.

== The Scenario

Your team is building an internal AI assistant for operations staff. The assistant must do more than chat -- it needs to look up employee records, check inventory systems, and query live data from external APIs. Today, staff switch between five different tools to answer one customer question. You are building an assistant that calls those tools automatically.

The challenge: most tool calling tutorials assume expensive GPU hardware. In this lab you will prove that an {intel_platform} CPU can handle agentic AI workloads -- because tool calling's stop-and-go pattern (short model outputs, long tool execution waits) plays to CPU strengths, not GPU strengths.

== What You Will BUILD

By the end of this lab you will have constructed:

* A connection to *{maas_model}* via Model as a Service -- tool calling enabled, running on Intel Xeon 6 via MaaS
* The complete *6-step tool calling protocol*, executed by hand so you understand every piece
* An *automated dispatch loop* in Python that handles the tool call lifecycle
* A *multi-tool application* where the model chains multiple function calls to answer complex questions
* *Advanced patterns* including parallel calls, error handling, and guard rails

There is no application UI. You build and run everything from the terminal using `curl` and Python.

== The Tool Calling Lifecycle

Tool calling follows a precise protocol. Every step in this lab maps to one part of the lifecycle:

[cols="1,2,1"]
|===
| Phase | What Happens | Module

| *Define*
| You describe available functions in JSON Schema
| 3

| *Request*
| The model returns a `tool_calls` array instead of text
| 3

| *Execute*
| Your code runs the function and collects results
| 3-4

| *Return*
| You send the result back as a `role: "tool"` message
| 3-4

| *Synthesize*
| The model incorporates the result into a natural answer
| 3-4

| *Chain*
| The model calls multiple tools in sequence to solve complex problems
| 5
|===

The model never executes code. It produces structured JSON requests. Your application handles execution, error handling, and returning results.

== Show → Learn → Do → Prove

* *Show:* inspect a real tool-call response from the model assigned to the
  seat.
* *Learn:* separate model selection, JSON tool contracts, application dispatch,
  tool execution, and final answer synthesis.
* *Do:* build a guarded Python dispatch loop and extend it from one mock tool to
  several tools.
* *Prove:* record the assigned model, the requested tool names and arguments,
  application results, final answer, namespace boundary, and cleanup. Economic
  conclusions require measured utilization and approved cost inputs.

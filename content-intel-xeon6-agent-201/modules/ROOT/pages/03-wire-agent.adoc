= Module 3: Wire the Agent
:navtitle: Wire the Agent

== Objective

Deploy the Solution Architect agent, connect it to the model and MCP tools, and get your first solution brief.

== Exercise 1: Inspect the System Prompt

The agent's behavior is defined by a system prompt, mounted as a ConfigMap.
The backend deployment in Module 2 installed it; now read it:

[source,bash,role="execute",subs=attributes+]
----
oc project {project_name}
oc project -q
----

[source,bash,role="execute",subs=attributes+]
----
oc get configmap advisor-prompt -o jsonpath='{.data.system_prompt}' | head -30
----

The prompt defines:

* *Persona*: "You are a Red Hat + Intel Solution Architect..."
* *Process*: Understand requirements → look up hardware → check platform → get architecture → generate brief
* *Output format*: Structured recommendation with executive summary, hardware tiers, platform components, and partnership value

This is the primary control surface. Change the prompt, change the behavior -- no code changes required.

== Exercise 2: Inspect the Agent

The solution-agent container connects to the Launchpad MaaS endpoint assigned
to this lab and reaches the co-located MCP tools through its namespace Service.

The lab provisioner has already generated and assigned a short-lived, model-scoped virtual key. Store the assigned endpoint in a ConfigMap and the assigned virtual key in a Secret so the deployment does not hard-code either value. Launchpad also injects the `launchpad-model-ca-bundle` ConfigMap so the agent verifies private cross-cluster model TLS without disabling certificate validation:

[source,bash,role="execute",subs=attributes+]
----
oc get pod -l app=solution-agent
export ADVISOR_API_URL="http://solution-agent:8082"
----

Check the agent's environment:

[source,bash,role="execute",subs=attributes+]
----
oc get deploy/solution-agent -o jsonpath='{.spec.template.spec.containers[0].env[*].name}' | tr ' ' '\n'
----

Key environment variables:

* `LITELLM_API_BASE` -- the Launchpad MaaS endpoint assigned to the lab
* `LITELLM_API_KEY` -- authentication
* `MCP_SERVER_URL` -- the Service for the tools sidecar in the same pod
* `ADVISOR_MODEL` -- which model to use for reasoning

The Secret contains the short-lived virtual key generated automatically for this lab order. The learner does not create or assign a MaaS key. The ConfigMap contains only the non-secret endpoint; the credential remains in the Secret.

== Exercise 3: Deploy the UI

Deploy the chat interface:

[source,bash,role="execute",subs=attributes+]
----
oc apply -f https://raw.githubusercontent.com/rhpds/launchpad/intel-guided-content-v1.0.14/content-intel-xeon6-agent-201/manifests/solution-ui.yaml
oc rollout status deploy/solution-ui --timeout=180s
----

=== Wait for the Solution Architect UI

The *Solution Architect* tab exists when the lab opens, but its application is
created by the command above. If you opened the tab before this step, a
temporary "not ready" page is expected.

Verify the namespace-local UI health endpoint before returning to the browser:

[source,bash,role="execute"]
----
for attempt in {1..40}; do
  curl -fsS http://solution-ui:8080/health >/dev/null && break
  echo "Waiting for the Solution Architect UI..."
  sleep 3
done
curl -fsS http://solution-ui:8080/health | python3 -m json.tool
----

For an external workshop, your access URL remains the instructor-provided Launchpad URL.
Return to *Open Lab* and refresh the *Solution Architect* tab.
Launchpad automatically proxies the application for your assigned seat. Do not open the raw OpenShift Route
in an external browser; the `apps.arena` hostname
is only the gateway's upstream target.

Confirm that the UI Route belongs to the tenant namespace. This is a diagnostic
check, not the participant browser URL:

[source,bash,role="execute",subs=attributes+]
----
oc get route app
oc project -q
----

== Exercise 4: First Conversation

Send a request via the terminal:

[source,bash,role="execute"]
----
ADVISOR_API_URL="http://solution-agent:8082"
curl -fsS -X POST "${ADVISOR_API_URL}/api/v1/advise" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "A retail chain needs real-time inventory prediction across 500 stores. Each store has 2 edge servers running legacy Windows applications. They currently run VMware with Oracle DB. Budget is $2M for the infrastructure refresh. They need sub-second predictions at each store."
  }' | jq '.'
----

Examine the response:

* `brief` -- The full solution recommendation
* `requirements` -- What the agent extracted from your query
* `hardware_options` -- Intel products the agent looked up
* `platform_capabilities` -- OpenShift features the agent identified
* `architecture` -- Reference architecture that matches
* `inference_log` -- Every LLM call and tool call with latencies

[sidebar]
****
*Record:*

* How many LLM calls were made? ___
* How many MCP tool calls were made? ___
* Total inference time: ___ ms
* Does the recommendation cite specific Intel SKUs? ___
* Does it name specific OpenShift operators? ___

Compare this to the raw model response from Module 1. The agent's response is backed by real data.
****

Now try the same question in the *Solution Architect* tab using the chat UI.

== Learning Outcomes

* An agent is infrastructure: model + tools + prompt, deployed as Kubernetes containers and pods
* The system prompt defines behavior; the model provides reasoning; the tools provide data
* LangGraph orchestrates the multi-step workflow automatically
* Every tool call and LLM call is logged -- you can audit exactly what happened

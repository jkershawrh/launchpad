= Track 1: Understand the Application Pattern

== Purpose

The source project's first track teaches the application pattern through a
fictional IT operations incident. You will first produce something useful: an
incident response package containing gathered evidence, likely causes, and a
proposed governed action. Then you will inspect how the orchestrator, three A2A
agents, MCP server, guardrails, and participant UI created it.

In a Launchpad workshop you already have a *pre-provisioned OpenShift runtime*
containing the same application services. You will inspect the local source
contract and exercise that request flow without starting a second copy of the
stack inside your seat. This keeps one lab consistent for every participant
while preserving the source track's learning objectives.

== Run Your First Workflow

Open the *Multi-Agent Workspace* tab. On the *Incident Workspace*, run the
following scenarios by entering each request in the *Fictional incident or operations request* box and
clicking *Investigate Incident*. Run the requests one after another so you can compare
their completed timelines and response packages.

[source,text]
----
Check the health of the fictional checkout service and prepare a verification task.
----

[source,text]
----
The fictional checkout API is slow after a deployment. Gather relevant evidence,
assess likely causes, and prepare a safe remediation task for operator approval.
----

Leave the response depth on its automatic setting. The first request should
choose a shorter path; the second should involve research, analyst, and
executor roles. Watch *Live Incident Response Progress*: the stages complete
one at a time because each agent receives the accumulated context from the
previous stage.

*Expected result:* both requests complete without a workflow error, and the
*Incident Response Package*, *Supporting Evidence*, and *Why this response
path was selected* sections update. *Prior incident runs* preserves the
completed history for comparison.

== Read the Incident Response Package

=== Gather Evidence

The research agent collects relevant fictional records and operational
knowledge. Its output is evidence for the next stage, not a final diagnosis.

=== Assess Likely Causes

The analyst correlates the gathered evidence, distinguishes observations from
inferences, and identifies useful next steps. The analyst does not make a
production change.

=== Prepare a Governed Action

The executor turns the accumulated context into a proposed task or response.
The package ends at a human approval boundary: a qualified operator must verify
the evidence and approve any real action.

== Inspect the Application Topology

Clone the exact source revision used to construct this lab:

[source,bash,role="execute",subs=attributes+]
----
git clone {source_repo} multi-agent-quickstart
git -C multi-agent-quickstart checkout {source_revision}
cd multi-agent-quickstart
----

Inspect the Docker Compose topology and application entry points:

[source,bash,role="execute"]
----
grep -E '^  (orchestrator|research-agent|analyst-agent|executor-agent|mcp-server|guardrails|ui):' docker-compose.yml
sed -n '1,180p' src/orchestrator.py
sed -n '1,160p' src/agent.py
----

Notice that each agent has its own service boundary. The orchestrator discovers
agents through A2A cards, MCP tools remain separate from inference, and
guardrails are called before and after model work.

== Follow One Query Through the System

When you click *Investigate Incident*, the participant UI sends the request and selected
workflow type to the orchestrator. With `auto` selected, the semantic router
classifies the request as `SIMPLE`, `MEDIUM`, `COMPLEX`, or `REASONING`. That
classification selects both the workflow depth and the model tier: a simple
request can go straight to the executor, a medium request can use research and
execution, and a complex or reasoning request can use research, analysis, and
execution.

The orchestrator discovers each service from its A2A agent card and sends each
step as an A2A `tasks/send` request. Before an agent calls a tool or model,
input guardrails screen the task. The agent may ask the separate MCP server for
structured external data, then calls the selected model. Output guardrails
screen the generated response before it returns to the orchestrator. The
result of one step becomes context for the next step, and the UI separates the
combined response into three boxes.

=== Why This Response Path Was Selected

This expandable section explains _why_ the request took its path. For automatic routing it shows
the active classifier, chosen workflow, selected model tier, classification
signal scores, agents involved, step count, and total latency. Compare the two
requests: the signal and workflow should change as the requested work becomes
more complex. If static routing is shown, the selected workflow was used
directly instead of a semantic classification.

=== Incident Response Package

This section shows the ordered contribution from each participating agent and
the time and actual model used for each stage. The research result becomes
context for the analyst, and the accumulated context becomes input for the
executor. These are AI-generated results, so the human-review notice is a
control boundary rather than permission to apply the recommendation.

=== Supporting Evidence

This section shows structured results returned by governed tools such as `lookup_record`,
`search_knowledge_base`, or `create_task`. MCP keeps deterministic data lookup
and actions outside the language model so they can be schema-controlled,
authorized, tested, and audited independently. This is external tool data, not
hidden model reasoning. A request that does not match a tool's trigger can
correctly show that no MCP tools were called.

== Optional Run Outside Launchpad

Docker Compose is the upstream local execution method. Run it on your own
workstation only after the workshop if you want to reproduce the local
topology. The pinned source README contains the required CPU, memory, model,
and environment setup. Do not try to run a nested Docker Compose stack inside
the Launchpad terminal.

== Track 1 Checkpoint

You have completed Track 1 when you can explain:

* what business result the incident workflow produces;
* why each agent is independently discoverable;
* how semantic routing changes workflow depth;
* why MCP tools are separate from the model; and
* where input and output guardrails run.

Use these observations to check your explanation:

* The business result is an incident response package: gathered evidence,
  assessed likely causes, and a proposed governed action that still requires
  human review.
* Each agent is independently discoverable because it publishes its own A2A
  agent card, service URL, and skills. The orchestrator learns that contract
  without importing the agent's implementation.
* Semantic routing changes workflow depth by mapping the query classification
  to a one-, two-, or three-agent path and an appropriate model tier. Choosing
  a workflow explicitly bypasses that automatic choice.
* MCP tools are separate because the model produces language while tools
  perform schema-defined data retrieval or actions that can be governed and
  audited independently.
* Input guardrails run before an agent calls MCP or the model. Output
  guardrails run after generation and before the result returns to the
  orchestrator.

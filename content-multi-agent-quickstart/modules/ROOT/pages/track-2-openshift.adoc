= Track 2: Build and Operate on OpenShift

== Purpose

Track 2 turns the architecture into an observable, changeable agentic
workflow. Launchpad has deployed a safe baseline to your assigned namespace,
injected a short-lived MaaS credential, configured service authentication, and
connected the Showroom terminal to your participant identity. You will run the
baseline, apply a non-secret executor policy, prove that the workflow still
works, and roll the change back.

You operate only your deployment. Cluster-administrator credentials are not
needed and must not be used.

== Learning Outcomes

After this track, you can:

* identify the OpenShift resources behind a multi-agent request;
* trace research, analysis, execution, MCP, and model boundaries;
* apply a configuration policy to one agent using namespace-scoped RBAC;
* validate the changed system through participant-visible behavior; and
* roll back safely while retaining evidence of what changed.

== Verify Your Boundary

[source,bash,role="execute",subs=attributes+]
----
test "$(oc project -q)" = "{project_name}"
oc auth can-i get pods -n {project_name}
oc auth can-i create deployments.apps -n {project_name}
oc auth can-i get pods -n partner-ai-launchpad
oc auth can-i get nodes
----

The initial `test` command is silent when the project is correct. The next two
authorization checks must return `yes`, and the
`partner-ai-launchpad` check must return `no`. Because `Node` is a
cluster-scoped resource, the last command normally prints
`Warning: resource 'nodes' is not namespace scoped` and then `no`. That warning
is informational; the final result must be `no`. A `Forbidden` response is
also an expected denial if you attempt a direct read instead of asking
`oc auth can-i`. These denials prove the seat is not a cluster-wide identity.

== Inspect the Deployed Baseline

[source,bash,role="execute"]
----
oc get deployments,pods,services,routes
WORKLOAD_POD="$(
  oc get pod -l app.kubernetes.io/name=multi-agent-seat \
    -o jsonpath='{.items[0].metadata.name}'
)"
echo "Workload pod: ${WORKLOAD_POD}"
oc get pod "${WORKLOAD_POD}" \
  -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'
oc rollout status deployment/multi-agent --timeout=5m
oc rollout status deployment/showroom --timeout=5m
----

The Deployment named `multi-agent` creates one seat-specific workload pod,
whose generated name starts with `multi-agent-`. The label
`app.kubernetes.io/name=multi-agent-seat` finds that pod without depending on
its generated suffix. It contains the `orchestrator`, `research`, `analyst`,
`executor`, `mcp-server`, `guardrails`, and `participant-ui` containers. A
separate Showroom pod supplies this guide and terminal. The model remains a
shared Launchpad MaaS service; it is not loaded once per participant namespace.

Open the *Multi-Agent Workspace* and remain on *Incident Workspace*. Expand
*Advanced response options*, open *Response depth*, and select
`comprehensive`. Enter this sanitized baseline request in *Fictional incident
or operations request*, then click *Investigate Incident*:

[source,text]
----
Investigate a fictional API error spike, analyze likely causes,
and create a remediation task.
----

Record the three agents, step count, routing choice, and whether MCP tool data
appears. This is the behavior your change must preserve.

== Apply an Executor Policy

The runtime Secret contains credentials. Do not edit or print it. The certified
Deployment provides a GitOps-safe, optional ConfigMap extension point for
non-secret learner policy. This policy lowers the executor's generation bound
without patching an Argo CD-managed Deployment field.

[source,bash,role="execute"]
----
oc create configmap workflow-policy \
  --from-literal=AGENT_MAX_TOKENS_OVERRIDE=48 \
  --dry-run=client -o yaml | oc apply -f -

oc rollout restart deployment/multi-agent
oc rollout status deployment/multi-agent --timeout=5m
----

Verify that the restarted executor process read the override:

[source,bash,role="execute"]
----
oc exec deployment/multi-agent -c executor -- \
  python -c 'import agent; print(agent.AGENT_MAX_TOKENS)'
oc get configmap workflow-policy -o yaml
----

The Python command must print `48`. The ConfigMap is referenced only by the
executor container and contains no credential.

Run the same comprehensive request again in the *Multi-Agent Workspace*.
Confirm that research, analyst, and executor still complete in order, MCP data
is present, and no workflow step reports an error. Then inspect the executor's
recent operational output without printing any Secret:

[source,bash,role="execute"]
----
oc logs deployment/multi-agent -c executor --since=5m | tail -20
----

This is a real runtime change: OpenShift restarted the compact workload pod and
the executor read the optional policy. The Deployment specification remains
owned by Git, while the A2A and MCP contracts stay unchanged.

== Roll Back and Clean Up

Return the seat to its certified baseline before continuing:

[source,bash,role="execute"]
----
oc delete configmap workflow-policy
oc rollout restart deployment/multi-agent
oc rollout status deployment/multi-agent --timeout=5m
test "$(oc get configmap workflow-policy --ignore-not-found)" = ""
test "$(oc exec deployment/multi-agent -c executor -- \
  python -c 'import agent; print(agent.AGENT_MAX_TOKENS)')" = "96"
----

Because the compact workshop topology co-locates all runtime containers in one
pod, changing one container rolls that pod once. A production design may split
agents into independently scaled deployments when isolation and rollout
independence are more important than workshop pod efficiency.

== Learner Evidence

[cols="2,2,2",options="header"]
|===
| Check | Baseline | After policy
| Agents involved | research, analyst, executor | research, analyst, executor
| Workflow errors | 0 | 0
| MCP tool data | present | present
| Executor token bound | 96 | 48
| ConfigMap after cleanup | absent | removed after verification
|===

Your values are the evidence that you changed an agent's operating policy
without changing its protocol contract or escaping your namespace.

== Track 2 Checkpoint

Track 2 is complete when you have captured the baseline, applied the executor
policy, repeated the three-agent workflow successfully, restored the original
deployment, and proved the temporary ConfigMap is gone.

= Run Multi-Agent Workflows

== Open the Participant UI

Select the *Multi-Agent Workspace* tab, then remain on its *Incident Workspace*
page. Enter each request in *Fictional incident or operations request* and click
*Investigate Incident*. The results appear below the request area. If you want
to verify the implementation before beginning, open
*Technical Details*, expand *Runtime health*, and click *Refresh*. Confirm
`Agents discovered: 3` and the agent names `research`, `analyst`, and
`executor`, then return to *Incident Workspace*.

Start with a simple fictional request:

[source,text]
----
Create a short task to verify the health endpoint for a sample service.
----

Leave response depth on the automatic setting. Inspect:

* the stages in *Live Incident Response Progress*;
* the ordered *Incident Response Package*;
* the governed *Supporting Evidence*;
* why the response path and model tier were selected; and
* the human-review boundary.

== Compare Workflow Depth

Run this sanitized operations scenario:

[source,text]
----
Investigate a fictional API error spike in the EMEA test environment,
analyze likely causes, and create a remediation task.
----

In *Multi-Agent Workspace*, expand *Advanced response options*. Open the
*Response depth* list, select `lightweight`, enter the request above in
*Fictional incident or operations request*, and click *Investigate Incident*.
Wait for that run to finish. Then select `comprehensive` from *Response depth*
and click *Investigate Incident* again with the same request. The comprehensive
path should involve research, analyst, and executor agents. Compare the stage
times and outputs in *Previous incident runs* rather than relying on a single
total.

== Call the API Directly

If the earlier orchestrator port-forward is no longer running, recreate it as shown in the previous module. Then call the workflow API:

[source,bash,role="execute"]
----
AGENT_AUTH_TOKEN="$(
  oc get secret multi-agent-runtime \
    -o jsonpath='{.data.AGENT_AUTH_TOKEN}' | base64 -d
)"
test -n "$AGENT_AUTH_TOKEN" || {
  echo "Unable to read the seat-specific agent token" >&2
  false
}
curl -fsS http://127.0.0.1:18000/api/v1/workflow \
  -H "Authorization: Bearer ${AGENT_AUTH_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "Summarize a fictional service incident and recommend next steps",
    "workflow_type": "comprehensive"
  }' | python3 -m json.tool
unset AGENT_AUTH_TOKEN
----

The token is read into a shell variable and never printed. It authorizes this
seat's UI and orchestrator request; the orchestrator uses the same protected
service boundary when it delegates A2A tasks.

If the API returns `401`, run the complete block again. The non-empty check
stops before `curl` when the seat-specific token was not loaded, instead of
sending an unauthenticated request.

The response must contain `steps`, `total_latency_ms`, `agents_involved`, and `ai_disclaimer`. Each step should name the responsible agent and report its own latency.

== What to Notice

The orchestration layer owns workflow state. Agents receive bounded tasks through A2A and return structured artifacts. MCP enrichment is a separate tool boundary, and model calls go through the Launchpad-provided endpoint. This separation lets each contract be tested and secured independently.

== Workflow Checkpoint

You are ready to continue when you can point to the response package,
supporting evidence, routing explanation, and per-stage latency for a completed
incident—and explain why the comprehensive workflow has more stages than the
lightweight workflow.
